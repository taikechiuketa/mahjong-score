## データへの影響

DBスキーマ・RLS・保存形式の移行は行わない。デプロイ作業では管理DB・公開DBへの書き込みを行わない。公開済みデータは別途JSONで退避した（181セット、1,456半荘、取得時のupdated_at 2026-11-15T16:09:49.057+00:00）。管理者用DBと端末の最新未送信入力は、この開発環境から認証取得できていないため、開発環境へ完全バックアップしたとは扱わない。

その代わり、改修版の最初の起動時に旧端末データ、最初の認証付き取得時に管理DBの完全なスナップショットを端末の別領域へ保護する。いずれもDB送信より先に行い、保護失敗時は操作を止める。ブラウザ保存は端末故障・ブラウザデータ消去への別媒体バックアップではないため、設定から全データと復旧コピーを書き出す機能を用意する。

## コードだけを旧版へ戻す

1. 現在のmainを別ブランチへ退避する。
2. 退避コミットのtreeを使い、現在のmainを親とする新しいコミットを作成する（履歴を強制巻き戻ししない）。または通常のrevertで今回の変更を打ち消す。
3. mainをその復旧コミットへfast-forwardで進める。公開完了後に入力画面・閲覧画面を確認する。
4. DBは書き戻さない。新しい版で保存された対局も旧形式のためそのまま読める。既存URLと端末キーは同じ。

旧版に戻すことと過去の対局データへ戻すことは別操作。通常はコードのみ戻し、その間に追加した対局を消さない。

## データの復旧が必要な場合

1. まず新しい入力と同期を停止し、現状の全データをバックアップする。
2. 改修版が使えるなら設定の復旧コピー一覧から対象日時・件数を確認し、端末にだけ復元する。
3. どの端末・DBにあるデータを残すべきか照合し、必要な対局を整理する。旧コピーを無条件にDBへ送らない。
4. 内容の確認後に保存操作でDBへ反映する。旧版で復元する場合は通常のtakechao-backup形式のJSONへ変換して既存の復元機能を使う。

復旧書き出しファイルのsnapshotsには複数形式がある。data.current/history/master、data.data.current/history/master、またはrawの旧3キーから標準バックアップを構成できる。認証情報は含まない。

## 検証

`npm ci && npm test`（Node 22以降）。実データ照合を含める場合は `TEST_PUBLIC_SNAPSHOT=/path/to/public-snapshot.json npm test`。実データファイルはリポジトリへコミットしない。

テスト対象：未ログイン時の非表示・サンプル廃止、自動取得、起動時書き込みゼロ、旧端末とDBの競合、接続失敗、コピー保存失敗、条件付きDB更新、既存履歴保持、公開反映失敗、未保存入力の集計除外、履歴編集保護、ログアウト、部分的な端末書き込みの復元、復旧コピーからの端末復元、4画面の導線、実データでの旧版との集計・R一致。

本番認証情報を用いた保存試験は未実施。公開後は所有者のログインで実データ件数・直近セットと保存状態を確認する。検証のための架空対局を本番DBへ追加しない。
