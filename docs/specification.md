# たけチャート 機能・データ仕様書

[画面説明](screen-guide.md)・[公開とロールバック](release-20261116.md)

2026年11月16日改修。GitHub Pagesと既存Supabaseを継続利用する。

## 1. 構成と互換性

| ファイル | 役割 |
| --- | --- |
| index.html | 既存の入力・履歴・集計と4画面の構造 |
| index-auth.js | 認証、起動時のDB取得、保存、競合確認、公開反映、ログアウト |
| data-safety.js | IndexedDBによる復旧コピー・同期基準の保存 |
| results.html | 公開成績、個人成績、レーティング、セット共有 |
| set-analysis.js / score-view.css | 入力・履歴・共有の固定ヘッダー、セット別着順分析、期間フィルターの表示 |
| rules.html | 公開ルール、点数表、共通ログインによる管理者編集 |

DBのテーブル・列・RLS・所有者ID・既存データ形式は変更しない。localStorageの mahjong-sheet-v2 / mahjong-sheet-archive-v1 / mahjong-player-master-v1 と takechao-cloud-session-v1 を維持する。旧版に戻しても保存済みデータを読める。

## 2. 認証と起動

所有者のメール・パスワード認証を利用する。保存セッションがあればrefresh tokenで更新する。所有者IDを検査し、DBの権限制御は既存RLSを利用する。クライアントの表示制御だけをアクセス制御とはみなさない。

起動時は管理画面を非表示にし、復旧領域を開いて旧端末の生データを保護する。その後認証・DB取得・妥当性検証・競合判定を行う。認証またはDB取得に失敗した場合は、空データを本番として扱わず送信も行わない。

ログイン後・セッション再開・再表示時の読み込みではDBに書き込まない。初回データがない場合は待機状態を表示し、ユーザー操作による保存でのみ初期行を作る。

Web Locks対応環境では同一ブラウザの記録タブを1つに制限する。認証トークン更新も同一origin内で直列化する。未対応ブラウザでもDBの更新日時による競合検出は維持するが、同一端末の複数タブ編集は避ける。

## 3. 一時保存・競合判定・復旧コピー

DBの管理スナップショットは current / history / master。端末の同形式データと最後に確認したDB基準を、オブジェクトのキー順によらず比較する。

基準が存在する場合は端末の差分を未送信と判定する。旧版からの初回移行で基準がなければ履歴・点数・チップ・独自マスターを確認する。名前だけで既存データを削除しない。サンプルと見られる空入力も、DB読み込み前の生データとして保護する。

差分のある端末とDBは自動上書きせず、復旧コピー作成後に選択画面を出す。DB選択時は最新データを再取得する。端末選択時も最新DBを退避し、DB更新日時を記録して編集を再開するが自動送信しない。

復旧領域は IndexedDB takechart-recovery-v1 / copies。内容のSHA-256と種類からIDを生成し、同じ内容の既存コピーは置き換えない。旧版起動前、DB読み込み前、DB送信前の管理データと公開データ、競合時、ログアウト前、復元前、ルール公開前を保護する。認証トークン・パスワードは復旧コピーに含めない。作成失敗時は該当する置換・送信・ログアウトを中断する。

端末復元は3キーへの書き込みを試み、途中失敗時は既に書いたキーを元へ戻す。クラッシュや端末故障まで含む完全なトランザクションではないが、事前のIndexedDBコピーから復旧できる。

履歴の未確定編集は takechart-history-draft-v1 に保護し、元の履歴が同一の場合だけ再開する。復旧ファイルは format:takechart-recovery / version:1 / snapshots。通常の全データバックアップは従来どおり format:takechao-backup / version:1。

## 4. 保存と公開

スコア入力は端末に一時保存する。「セットを保存」はarchiveIdで履歴を追加・更新してからDBへ反映する。「セットを終了」は履歴保存後にidle状態へ移す。新規セット作成時も進行中があれば保存確認を行う。

DB送信前に最新の管理行と公開行を取得して復旧コピーを作る。管理行はowner_idと既知のupdated_atで条件更新する。一致しなければ送信を停止し競合確認へ移る。存在しない行へのPOSTは明示的な保存操作時だけ。履歴セット数または半荘数が減る送信は、事前確認を追加する。

管理保存と公開更新は別リクエストであり、DBトランザクションではない。公開更新前に管理行の版を再確認し、公開行も以前のupdated_atを条件に更新する。公開失敗時は管理保存済み・公開反映待ちを区別し、再試行で公開反映を回復する。通信失敗や競合は端末データを消さない。

public results / details-v1 / sets-v2 の形式と公開範囲は維持する。公開データはhistoryだけから作り、未保存入力は含めない。進行中でも履歴へ保存した同一セットは公開対象になる。

## 5. 対局・集計仕様

種目は三麻normal（3人）、四人三麻north（4人）、四麻yonma（4人）。スコアは整数。未入力と抜けskipを区別する。入力人数不足・非整数・ポイント合計不一致・チップ合計不一致は保存時の警告対象。精算は累計pt×倍率＋チップ×チップレート。

管理側の通算成績・個人成績・レーティングはhistoryの保存済みスナップショットだけを集計し、現在入力中の同一セットを足さない。未送信の履歴変更は公開側と一時的に異なり得るため保存状態を表示する。履歴画面では進行中セットを別途表示し、archiveIdで重複表示を避ける。

期間は全期間、今月、前月、月間ランキング、今年、範囲指定（両端を含む）。混在セットのチップ・対応収支は全種目でのみ含め、種目指定ではその種目だけのセット分を含める。

必要人数の整数スコアがそろった半荘で順位を計算する。同点は同順位。トップ率・ラス率は有効な順位のある半荘が母数。レーティングは初期1500、期待値1/(1+10^((相手R−自分R)/400))、実績は勝1・同点0.5・負0、各相手との実績−期待値の平均×24。必要人数・ID重複なし・合計0の半荘だけを対象に日付・伝票番号・半荘順で計算する。20半荘未満は暫定。

既存の参加者名・ポイント・チップ・archiveId・倍率・レート・日付等を変換しない。既存公開181セットの全種目・種目別集計とRについて、旧版との一致を検証した。基本のポイント・順位・レーティングの計算式は維持している。

### スコア表とセット別着順分析

入力スコア表、履歴の半荘別スコア、セット共有の半荘別スコアは、最大58dvh（非対応環境は58vh）の独立スクロール領域に収める。theadをtop:0、半荘列をleft:0にsticky固定する。交差セルは両方の方向へ固定し、スクロールするセルより手前に描画する。入力表の累計ptは下端固定。半荘追加時は表の中だけを末尾へスクロールする。長い対局者名は入力ヘッダーで折り返し表示する。

セット別着順はset-analysis.jsで管理・公開・セット共有が同じ計算を利用する。各半荘で必要人数の整数スコアが入力された場合に限り、自分より高得点の人数+1を順位とする。同点は同順位。抜け・未入力・人数不足・非整数の半荘は対象外。合計0の検証は入力保存時の既存チェックを利用し、着順判定は従来のsetResultsと同じく必要人数の整数入力を条件とする。

割合は各参加者の順位判定可能な半荘数を分母に、着順回数÷分母×100を小数1桁で表示する。種目混在時は全種目を合算する。四人種目で有効な参加が一度もない人の4着は「—」。0半荘の割合は「—」。着順回数は既存データから都度計算し、DBには追加保存しない。

### 通算集計とR推移の期間

通算成績のstatsPeriod / Month / From / ToはtotalsPanel内に置く。レーティング表には「現在R：全期間」を表示し、現在R・対象半荘・直近の増減は全期間から算出する。

R推移は表の下のratingTrendPeriod / Month / From / Toという独立したフィルターを使用する。選択肢と日付判定は通算フィルターと共通だが選択状態は別。過去からの累積Rを再計算せず、全期間のR履歴から対象期間の点を表示する。期間の開始直前Rから描画する従来の挙動を維持する。レーティング表から開く個人成績は全期間に固定し、通算表から開く個人成績は通算の選択期間を使う。

## 6. 対局日・伝票番号の編集

入力画面の「日付・番号を編集」から、進行中・履歴編集中のセットのdate / sequenceを変更できる。dateは実在する西暦4桁の日付（端末保存はYYYY/MM/DD）、sequenceは1以上の安全な整数。内部archiveId、参加者、点数、チップ、倍率、取り込みキーは変更しない。

変更候補と既存履歴・別の進行中セットを照合し、同じ日付・連番を拒否する。自分自身のarchiveIdまたは編集中の履歴indexは重複判定から除く。変更確定時とセット保存時に検証する。既存データに重複があっても、日付・連番を変えない従来の編集は妨げない。

変更前にbefore-set-identity-edit復旧コピーを作成する。コピーまたは端末保存失敗時はstateを変更しない。端末への適用では日付・連番だけを変えた複製を一時保存し、DBには自動送信しない。履歴編集では既存の編集ドラフトへ保護する。「セットを保存」で従来どおり同じarchiveIdまたは履歴indexのレコードを更新し、別のセットとして追加しない。

対局日による期間フィルターと日付・連番によるR計算順は変更後の値を使う。共有URLは日付・連番を含むため変更後に再発行が必要。旧URLへの別名・リダイレクトは設けない。既存データの一括変更・DB移行は行わない。

## 7. 共有・ルール・ログアウト

既存共有URL results.html?date=対局日&set=伝票番号 を維持する。同一キーが重複する場合リンクを出さない。公開ページは初回・30秒ごと・再表示時に更新確認し、変更なしの応答は[]。既存公開設定とランキング非表示の意味は維持する（履歴の名前非公開とは別）。

ルール編集は同じ保存セッションを更新して利用し、所有者確認と旧revisionによる条件更新を行う。旧本文を端末へ保護してから公開する。

ログアウトは現在端末のセッションをlocalスコープで失効要求し、localStorageのセッションを削除、管理画面を隠す。未送信入力は確認後に保護する。失効要求の通信失敗は区別して表示する。発行済みアクセストークンの即時無効化は保証しない。ロールバック互換性のため管理データの既存3キーは保持する。暗号化保管・端末所有者からの秘匿機能ではない。
